Design doc

feature-skills webapp

A self-hosted, single-tab home for feature docs. Replaces tab-grabbing with an inbox.

Status: design · Target stack: Python + Starlette + Jinja2 + SQLite · Authored 2026-06-03 (Claude Opus 4.7 from a conversation with Nigel)

TL;DR

The HTML migration left every feature doc as a static file in ~/.claude/feature-docs/<project>/<feature>/. Skills open each doc in a new Chrome tab, which steals focus from whatever you're reading. The webapp replaces that with a single always-open tab that pushes new docs into an inbox rather than into your face — and adds a cross-project home, persistent click-to-comment, real read-state tracking, and eventually search and history.

Build in two stages. Parallel mode first: the webapp reads dev-store files as-is; skills barely change. Then cutover: SQLite becomes canonical, skills talk to the webapp via MCP, click-to-comment + synthesis forms POST instead of round-tripping through the clipboard.

1Why a webapp

Three problems the static dev-store HTML doesn't solve well, in order of how much they hurt today:

  1. Tab focus stealing. Every skill that writes a doc runs google-chrome <path> &. Chrome grabs focus, you lose your place. This isn't a small annoyance — it derails whatever you were doing every time the agent surfaces something. The webapp fixes this by being one persistent tab that receives docs rather than interrupting you with them.
  2. "What do I need to look at?" has no answer. The dev-store grows. Docs accumulate. Some are awaiting your input (synthesis docs), others are informational (context, requirements re-renders), others are stale. Today the only way to find out is to open Chrome history or grep the dev-store. An inbox with "needs response" vs "new since last visit" is the natural fix.
  3. Cross-project tracking doesn't exist. One tracker per project, one set of contexts per project. As more projects adopt the workflow (kea, waddles, retail-backend, feature-skills itself), the fragmentation grows. A cross-project home view answers "what's active right now" across everything in one place.

The webapp was the original endpoint of the HTML migration — see the "Webapp deferral" section in the migration's planning doc. The migration deliberately structured the dev-store HTML so a webapp could be a thin lens over it without another data-shape change.

2Design principles

  • Single tab. Nigel keeps one webapp tab open in Chrome. All docs render in-place. New docs arrive as inbox cards, not new tabs. Skills stop opening Chrome.
  • Local-only by default. Runs on localhost:<port>. Data is sensitive (work-in-progress repo docs). No cloud, no auth needed beyond loopback.
  • Graceful degradation. If the webapp is down, the dev-store HTML still works directly in Chrome. Skills detect "webapp unreachable" and fall back to opening the file as today. The webapp is a UX improvement, not a hard dependency.
  • Inbox over tracker. The home view is an inbox of what needs attention, not a comprehensive tracker. The tracker is a sub-view. Default the user lands on action items.
  • HTML rendering, server-side. Jinja2 + Starlette, server-rendered, HTMX for interactivity. No SPA framework. No build step. Familiar territory.
  • SQLite is canonical (eventually). Stage 1 the dev-store files stay canonical and SQLite is an index. Stage 2 SQLite holds the docs themselves and the dev-store files become an export target (or disappear).
  • Skills talk via MCP. The bridge between feature-skills and the webapp is an MCP server. Skills call typed tools (tracker_move_to_in_progress, feature_save_context, etc.) rather than editing files. This happens at Stage 2; Stage 1 skills still write files.
  • Read state is a first-class concept. Every doc has a "last read at" timestamp. Every action-required doc (synthesis, click-to-comment-pending) has an explicit completion state. The inbox UI is derived from these.

3Architecture

ComponentTechJob
Webapp Python 3.14, Starlette, Jinja2, HTMX Renders HTML; serves API endpoints for inbox / read-state / comments / synthesis responses; pushes SSE events.
Storage SQLite (stdlib) Stage 1: index over dev-store files; tracks read-state, comments, synthesis responses. Stage 2: holds doc content directly.
Realtime Server-sent events (SSE) One persistent EventSource per tab. Webapp pushes "doc X changed" to clients. Inbox auto-refreshes.
Skill bridge MCP server (Stage 2) Typed tools the skills call instead of writing files. Stage 1: skills still write files; webapp picks them up via filesystem walker.
Runtime systemd user unit Webapp starts on login; restarts on failure. systemctl --user status feature-skills-webapp.

4Data model

Sketch (Stage 1 — index over files; Stage 2 adds doc content):

projects(id, name, repo_path, created_at)
features(id, project_id, slug, status, owner, notes, created_at, updated_at)
documents(
  id, feature_id, type,                  -- 'context', 'requirements', 'plan',
                                         -- 'requirements-feedback-1', etc.
  source_path,                           -- dev-store file path (Stage 1)
  content_html,                          -- Stage 2 only
  metadata_json,                         -- checklist state, section IDs, etc.
  source_mtime, created_at, updated_at
)
read_state(document_id, last_read_at)
synthesis_responses(
  document_id, item_num, response, routine_flag, updated_at
)
comments(
  id, document_id, excerpt, text,
  status,                                -- 'pending', 'integrated', 'dismissed'
  created_at, integrated_at
)
events(
  id, document_id, event_type,
  payload_json, created_at
)

The events table is the audit log — drives the inbox ("docs with events newer than last_read_at, grouped by type") and gives you the activity feed for "what did the agent do overnight."

5Migration path

Stage 1 — Parallel mode. The webapp is a lens over the dev-store. A filesystem walker discovers files, indexes into SQLite, serves them via Jinja templates. Skills don't change their write path. Two things are new from the user's POV:

  • The webapp tab shows an inbox + cross-project view.
  • Click-to-comment + synthesis forms POST to the webapp instead of building a clipboard blob. Comments persist in SQLite across re-renders.

Skills get one change: drop the google-chrome calls (or make them conditional on "webapp not running"). The user already has the tab open.

Stage 2 — Cutover. The MCP server lands. Skills call typed tools instead of writing files. SQLite holds the canonical doc content; the dev-store becomes an export target (so that the parallel-mode fallback still works if the webapp dies). The migration is per-skill, not a big bang: feature-context moves first (simplest write surface), then the synthesis-producing skills, then the rest.

Skills that read docs (feature-implement, feature-review, feature-iterate) gain a read-via-MCP path; the dev-store file path becomes the fallback.

6MVP feature breakdown

Each feature below is sized to be a candidate for the feature-skills workflow — capture as a context.html, then feature-requirements → feature-plan → feature-implement as usual. Dependencies between features are called out; pick by topology.

Pill key: small ≈ a few hours; medium ≈ a session or two; deps = upstream features.

webapp-skeleton

small

The "hello world" that proves the stack — a Starlette app on localhost serving a single static page, a SQLite DB with an empty schema, and a systemd user unit so it starts on login.

Motivation

Everything else depends on having the process running and a place to put data. Get the bones in first.

Scope

  • Project layout: app/ (Starlette routes + Jinja templates), db/ (schema + migrations), bin/ (entry point).
  • One route, /, that renders a "feature-skills webapp" placeholder.
  • SQLite database with empty tables (per the data model in §4). Numbered SQL migrations.
  • systemd user unit at ~/.config/systemd/user/feature-skills-webapp.service.
  • Health check route /healthz.

Design notes

  • Use the same Starlette + Jinja2 + numbered-SQL-migration pattern kea uses. Nigel is fluent in it.
  • Listen on 127.0.0.1 only — no auth, no remote access.
  • Pick a port — suggestion: 8800. Configurable.

doc-discovery

medium deps: webapp-skeleton

Walk ~/.claude/feature-docs/<project>/, identify docs by their <meta name="feature-doc-type"> tag, and index into SQLite. Re-walk on demand and via filesystem watch.

Motivation

The webapp needs a model of what docs exist. Walking the filesystem on every request is slow; an index makes the inbox and project views cheap. Stage 1 keeps the files canonical and re-discovers from disk; Stage 2 retires the walker.

Scope

  • Walker module that recurses ~/.claude/feature-docs/, extracts project + feature slug from the path, reads <meta name="feature-doc-type"> from each .html file, and upserts to documents.
  • Tracks source_mtime per doc; only re-parses on change.
  • Triggered on startup, periodically (every N minutes), and on demand via an admin endpoint.
  • Filesystem watch via inotify / watchfiles for sub-second freshness (Linux-only is fine).
  • Emits an events row per discovered change for the activity feed and SSE push.

Design notes

  • Synthesis docs in .feedback-archive/ get indexed with status archived — visible in history, not in the live inbox.
  • features.html at the project root is its own doc-type — track separately from per-feature docs.

Open questions

  • What's the right inotify-vs-poll tradeoff if the user has the dev- store on a network mount? (Probably they don't; punt.)

read-state

small deps: doc-discovery

Track last_read_at per document. Stamp it on every page view. Drives "new since last visit."

Scope

  • On every doc-view request, upsert read_state(document_id, last_read_at=now()).
  • Helper: "is this document unread?" = max event timestamp > last_read_at.
  • One bulk "mark all read for this project" admin action.

Design notes

  • Single user — no need for a user table. Hardcode the read-state to a single row keyed by document.
  • Stamp on page render, not page close. Closer-to-correct is the enemy of perfect-and-complex.

inbox-view

medium deps: doc-discovery, read-state

The Home page. Cards grouped by category: "Awaiting your input", "New since last visit", "In progress", "Recently shipped". Cross-project by default.

Motivation

The headline UX. Without this, the webapp is just a static-file server with extra steps.

Scope

  • Route / renders the inbox.
  • Categories computed from SQLite:
    • Awaiting your input: synthesis docs with at least one item that has neither a synthesis_responses row nor a routine_flag.
    • New since last visit: documents with events newer than read_state.last_read_at.
    • In progress: features with status='in_progress', regardless of whether their docs have new events.
    • Recently shipped: last N features moved to status='done' (e.g. last 5, last 30 days).
  • Each card: project + feature + doc type + last activity timestamp + a primary action ("Open", "Respond"). Clicking a card opens the doc in-place (same tab).
  • Top of page: per-project filter chips, "show all" default.

Design notes

  • An "In progress" feature can simultaneously be in "Awaiting your input" — that's OK; show it in both with cross-references.
  • Done-section dedup: don't show a feature in "Recently shipped" if its ship event was >30 days ago.
  • Empty state: "Nothing's waiting for you" with a link to project views.

doc-view

medium deps: doc-discovery, read-state

Render an individual doc in the webapp. Reuses the existing template HTML; the webapp wraps it with chrome (project / feature / breadcrumbs) and stamps last_read_at.

Scope

  • Route /<project>/<feature>/<doc-type>.
  • Read the source file's HTML body (the <main> section + any TOC) and render it inside a webapp shell with breadcrumbs.
  • Stamp read_state.last_read_at on render.
  • Sibling-doc nav (prev/next across context → requirements → plan → review).

Design notes

  • Stage 1: pass through the existing CSS embedded in the source files. Don't try to restyle.
  • Stage 2: pull just the body, render via the webapp's own templates so we control the chrome.

synthesis-response-capture

medium deps: doc-view

Replace the synthesis doc's "Copy responses → paste JSON in chat" round-trip with a form that POSTs straight to the webapp. Responses persist in SQLite; the agent reads them on its next turn.

Motivation

Today, Nigel fills in textareas, clicks "Copy responses", switches to the Claude tab, pastes JSON, the agent parses. Friction every cycle. With the webapp, the form posts back, the agent calls synthesis_get_pending and finds them.

Scope

  • The synthesis HTML (feedback-template-derived) gets a small JS change: instead of building clipboard JSON, POST to /api/synthesis/<document_id>/responses.
  • The webapp stores each response in synthesis_responses, keyed by item number.
  • Routine flags (the "discuss this routine item" mechanism) save the same way.
  • Skills (Stage 2) read pending responses via MCP. Stage 1 fallback: a CLI command feature-pending-responses <feature> dumps the JSON the agent would expect.

Design notes

  • Keep the clipboard "Copy responses" button working as a fallback for when the webapp is down.
  • Save responses on blur (debounced), not just submit — don't lose work if the tab crashes mid-fill.

Open questions

  • How does the agent know responses are ready? Two answers: it asks ("when you've filled in the synthesis, tell me"), or the next tool-call sees them. Probably the former for now.

comment-capture

medium deps: doc-view

Click-to-comment annotations on narrative docs (context / requirements / plan) save to the webapp instead of clipboard JSON. Each comment persists across re-renders.

Motivation

Today, click-to-comment annotations live in browser memory and die when you Copy-paste them. If the doc gets re-rendered before you copy, comments are lost. The webapp solves both: persistence in SQLite, plus the round-trip is just a tool call, not clipboard surgery.

Scope

  • The click-to-comment widget in the templates POSTs each comment to /api/comments/<document_id> on save.
  • Comments persist in the comments table keyed by document.
  • The doc renderer pulls existing comments at view time and re-displays them in the rail.
  • When a comment is integrated by the agent (later), it's marked status='integrated' — keeps the audit trail but visually dims.
  • Skills read pending comments via MCP (Stage 2). Stage 1: CLI fallback feature-pending-comments <feature>.

Design notes

  • Excerpts may not match the current doc body after a re-render (the anchored text changed). Store the comment anyway; render with a "anchor-lost" indicator. Don't drop user content.
  • Keep the "Copy comments" button working as a fallback.

sse-refresh

small deps: inbox-view, doc-discovery

Server-sent events stream from the webapp to the open tab. When a new doc lands or an existing one changes, the inbox card list refreshes without a manual reload.

Scope

  • SSE endpoint /events. One persistent connection per open tab.
  • Webapp pushes an event for every events row insertion (filtered by event type — discovery, comment, response, ship).
  • Inbox-page JS listens via EventSource, refreshes the affected card or re-renders the inbox section.
  • HTMX swap on the inbox card list when events arrive (simpler than hand-rolled).

Design notes

  • Drop the connection cleanly on tab close. Reconnect on tab focus.
  • Throttle high-frequency events (a flurry of discovery events shouldn't repaint 50 times in a second).

skill-integration-parallel

small

Update feature-skills SKILL.md files: stop opening Chrome unconditionally; instead, tell the user in chat where the doc is and that the webapp will pick it up. Lives in the feature-skills repo, not the webapp.

Scope

  • Every SKILL.md that currently runs google-chrome ... & drops the call. There are ~5 places (context, requirements, plan, review synthesis, review feedback).
  • Replace with a chat message: "Wrote ~/.claude/feature-docs/<project>/<feature>/<doc>.html. Your webapp tab will show it in the inbox."
  • Optional: detect webapp reachability via curl -fsS localhost:8800/healthz and fall back to opening Chrome if it's down (graceful degradation per design principles).

Design notes

  • Independent of the webapp itself — can ship the day the webapp's inbox view works, even if everything else lags.
  • The fallback-to-Chrome detection is nice but not blocking; v1 can just drop the chrome calls and document the requirement that the webapp is running.

7Post-MVP / deferred

Not for the first cut. Listed so the agent picking up MVP has the wider picture.

  • mcp-server — typed MCP tools that replace skill file-writes. The Stage-1-to-Stage-2 pivot point. Probably the first thing to add after MVP works.
  • search — SQLite FTS5 over doc bodies. "Find all features mentioning dao-boundary".
  • history-view — preserve previous doc versions on re-render. Diff between rounds.
  • cross-project-tracker — single view of all in-progress features across all projects.
  • dependency-graph — features declare dependencies on others; surface blockers in the inbox.
  • activity-feed — chronological audit log of skill writes and your responses. Helpful for picking up after a break.
  • multi-machine-sync — depends on infrastructure choice (chezmoi-managed SQLite? a small VPS? syncthing?). Deferred.
  • features-tracker-edit-UI — edit tracker rows from the webapp without going through a skill. Maybe; might cleanly stay skill-only.
  • notifications — browser Notification API for "synthesis is ready for you". Opt-in per category; easy to overdo.

8Open questions

  • Where does the webapp live as a git repo? ~/src/nigelmcnie/feature-skills-webapp/ as a sibling to feature-skills/, or ~/src/nigelmcnie/feature-skills/webapp/ as a subdir? Sibling is cleaner if it's standalone (it is); subdir is fewer moving parts. Resolve before webapp-skeleton.
  • Process supervision: systemd user unit is the suggestion. Alternative: ~/.config/autostart/ entry. systemd is more robust (restarts on crash); autostart is simpler.
  • How does the agent know synthesis responses are pending? Probably: the user tells the agent ("I've filled it in"). Stage 2 MCP could have a has_pending_responses tool but is-the-user-done is fundamentally a conversation signal.
  • SQLite location. ~/.claude/feature-docs/_webapp.db (next to the data) or ~/.local/share/feature-skills-webapp/db.sqlite (XDG)? The former keeps everything together for chezmoi-management; the latter follows XDG conventions.
  • Authentication. Localhost-only is enough for v1. If you ever expose the webapp on the network (e.g. work laptop reading from home desktop), revisit.
  • Chrome tab survival. What happens if the tab gets closed accidentally — does the agent re-open it on the next skill run, or is the user expected to keep it open? Probably the latter; could add a "click here to open the webapp" message in skills if the user seems confused.
